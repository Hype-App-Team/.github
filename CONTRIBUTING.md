# Правила совместной разработки в Hype-App-Team

Этот документ описывает единый рабочий процесс для участников команды и ИИ-агентов во всех репозиториях организации (`hype-frontend`, `hype-backend`, `hype-ml`).

## 1. Ветки и коммиты (Trunk-Based Development)

- Основная ветка `main` всегда должна собираться, проходить все тесты и быть готовой к релизу.
- Любая задача делается в короткоживущей ветке от свежего `origin/main`:
  - `feat/<scope>-<short-slug>` — новая функциональность;
  - `fix/<scope>-<short-slug>` — исправление ошибки;
  - `chore/<scope>-<short-slug>` / `docs/<scope>-<short-slug>` / `refactor/<scope>-<short-slug>`.
- Заголовки коммитов и Pull Request оформляются по **Conventional Commits**:
  - `feat(map): добавить кластеризацию пинов при малом зуме`
  - `fix(auth): проверять срок жизни initData с допуском 30 секунд`
  - `feat(api)!: перевести контракт /v2/places на курсорную пагинацию` *(только при согласованном мажорном обновлении контракта)*.
- Вливание в `main` — только через **Squash Merge** после зелёного CI и ревью.

## 2. Локальная настройка защиты (обязательно после клонирования)

В каждом репозитории выполните один раз:

```bash
make setup
```

Команда активирует версионированные `.githooks`:
- `pre-commit` — блокирует случайный коммит `.env`, ключей, `.db` и токенов, а также проверяет архитектурные границы;
- `pre-push` — блокирует случайный прямой `git push` в `main`.

## 3. Контракты между репозиториями

Репозитории развязаны так, чтобы поломка или эксперимент в одном репо никогда не роняли сборку остальных:

- **`hype-ml` → `hype-backend`:**
  - В коде: версионированный wheel `gde-hype-ml` с проверкой `SHA256SUMS` (обновляется явно скриптом `./scripts/upgrade-ml-wheel.sh vX.Y.Z` через PR в `hype-backend`).
  - По сети: HTTP-протокол `POST /extract` + `GET /health` по схеме `contracts/extraction.schema.json`.
- **`hype-backend` → `hype-frontend`:**
  - Спецификация `contracts/openapi.v1.json` генерируется из FastAPI и проверяется в CI на отсутствие несовместимых удалений маршрутов и полей.
  - Обновление контракта во фронтенде выполняется через `./scripts/sync-openapi.sh` в отдельном PR.

## 4. Единая проверка перед отправкой PR

Перед открытием PR (и перед завершением любой задачи ИИ-агента) выполните:

```bash
make verify
```

Если `make verify` падает — PR не готов к вливанию. Запрещено отключать тесты (`.skip`, `xfail`), ослаблять правила типов или линтеров ради «зелёного» пайплайна.

## 5. Релизы и выкатка

- Релизы версионируются по **SemVer** (`v0.1.0`, `v0.2.0`, `v0.2.1`).
- Создание тега `vX.Y.Z` запускает `release.yml`, который публикует неизменяемые артефакты (GHCR-образ с привязкой к SHA256 digest, wheel или статический архив + `SHA256SUMS` + автогенерация Release Notes).
- Выкатка на любой сервер (`staging`, `prod-ru`, `prod-eu`) запускается через `deploy.yml` или скрипты `deploy/rollout*.sh`, включает прогрев и проверку `/health` до переключения трафика и автоматический откат за секунды при неуспехе.
